# Harness —— 成本核算与阶梯扫描

靶场是被测对象，harness 是量具。

```bash
botwall scan                             # 全 profile × 全攻击实现
botwall scan -p api-signed -a signed     # 指定组合
botwall scan --mode blind                # 测投毒与排障成本
botwall scan --proxy-tier residential    # 换代理档位重算
botwall attackers                        # 列出攻击实现及申报工时
botwall rates                            # 看当前价格表
```

---

## 计量是强制的

攻击实现拿到的 `BW_TARGET` 指向 harness 的计量反向代理，**不是靶场**。它不知道靶场的真实地址，因此无法绕过计量。

| 项 | 记账方式 | 攻击实现能否影响 |
|---|---|---|
| 请求数、字节数、状态码 | 计量代理 | 否 |
| 拦截原因码 | 计量代理解析 403 响应体 | 否 |
| CPU 时间 | `getrusage(RUSAGE_CHILDREN)` 前后差 | 否 |
| 记录真伪 | harness 调靶场的 `verify_record` | 否 |
| **逆向工时 `dev_hours`** | **manifest 申报** | **是** |

最后一行是唯一不可核实的量，所以它在输出里**永远与实测量分列**，只在 `total` 里合并。把二者悄悄加成一个数，读者就无法判断哪部分可信。

CPU 用 `RUSAGE_CHILDREN` 而不是墙钟：这个计数器只统计已回收的子进程，而靶场进程在整个测量期间一直活着不被回收，所以差值精确等于攻击进程的 CPU。墙钟里混着计量代理的转发开销，只作诊断量上报。

### 真值校验不能省

blind 模式下靶场返回 **HTTP 200 + 投毒数据**。只统计状态码会把投毒响应算成成功，从而高估通过率、低估重试放大系数 `R`、最终低估单位成本。harness 对每条记录调 `verify_record`，`R = 吐出条数 / 已验证为真的条数`。

## 攻击实现

它们之间**唯一的差别是 `headers()`**，也就是在成本阶梯上爬了几级。差异被压缩到一个方法上，测出来的成本差才只可能来自阶梯级别，不可能来自主循环写法的不同。

| | 级 | 多做了什么 | 申报工时 | 成本落在哪 |
|---|---|---|---|---|
| `naive` | L0 | 裸 GET | 0.1h | — |
| `spoofed` | L0 | 浏览器 UA + TLS 指纹 | 0.5h | 边际≈0 |
| `signed` | L1 | 复现 `derived` 档签名 | 6h | **一次性工时** |
| `enveloped` | L4 | 自洽环境快照 + `runtime` 档签名 | 10h | 一次性工时 |
| `browser` | L4 | 真浏览器跑站点自己的 `sign.js`，不逆向 | 1.5h | **持续边际** |
| `traced` | L5 | 合成类人轨迹 | 14h | 一次性工时 |

`browser` 是这里唯一走另一条经济路径的实现：它不逆向签名，让 Playwright 驱动一个真 Chromium 加载靶场页面、执行站点自己的 `signedFetch`。代价从"一次性逆向工时"换成了"每次采集都要跑一个浏览器"的持续边际成本——正是"能不能不用浏览器"这个论点的两端。它也是唯一真正付出浏览器 CPU 与整页流量的实现。

它过不了 `hardened` 的 paranoid WebGL 校验（headless 软件渲染是 SwiftShader），这个边界本身是一条结论：运行时层的严格档要逼出的正是**真实 GPU / 真实设备**，成本在那一步才真正跳到另一个量级。

### 一条靠测试强制的完整性约束

攻击实现**不许 import 靶场的 `app.signing`**。能 import 就等于抄答案，申报的工时和测出的成本全是假的。`test_attackers_do_not_import_range_internals` 用 AST 检查每个源文件（含公共骨架 `_base.py`），不靠自觉。

同样有测试禁止攻击实现内置任何指向外部主机的地址。

### 协议

```
输入   环境变量 BW_TARGET / BW_ITEMS_WANTED / BW_PAGE_SIZE
输出   stdout 逐行 JSONL，每行一条采到的记录
诊断   stderr（单独捕获，不参与计量）
退出   0 = 采够了，非 0 = 放弃
```

语言不限，进程边界就是接口边界。当前实现都是 Python，但换成 Go/Node 只要守住这个协议即可。

## 实测结果（v0.1）

`botwall scan -p cdn-standard -p api-signed -n 60`，价格表 v1，数据中心代理档。完整结果见 `results/v0.1-scan.json`。

```

naive        L0      0      ∞           ∞       0.02         ∞    ja3_absent
spoofed      L0     60   1.00×   1.50e-04       0.08      0.08    —
signed       L1     60   1.00×   1.60e-04       0.96      0.96    —

  → 最优：spoofed（L0），0.08/万条 · 误判成本：错选 traced 要多付 28.0 倍

══ api-signed [diagnostic/gate] ══
naive        L0      0      ∞           ∞       0.02         ∞    ja3_absent
spoofed      L0      0      ∞           ∞       0.08         ∞    sign_missing
```

实测列在重复运行之间会有几个百分点的波动，来自 CPU 计时噪声；这是量级结论，不是精确值。摊销列是确定性的（申报工时 × 价格表）。

### 三条读得出来的结论

**1. 纯 HTTP 方案的成本几乎全是一次性逆向工时，边际成本可以忽略。**

`signed` 的实测边际在 `1e-4` 量级，而它的摊销工时（在年采千万条下）是 `0.96`——差四个数量级。这正是成本模型里说 L1 特殊的原因：它付出的是一次性工时而非持续边际成本，所以**采集量越大越划算**。推论对防御方直接有用：针对这类对手，抬边际成本（加难度）几乎无效，抬一次性工时（加检查项数量和多样性）才有效。

**2. `browser` 的边际成本是 `signed` 的约 48 倍，却因为省掉逆向工时而在中等规模下总成本最低。** 这不是矛盾，是两条经济路径的分工——见下节的交叉点。这个 ~50× 是真实测出来的：`browser` 加载整页约 800 KB 资产（JS/CSS/图片/字体），`signed` 只取约 11 KB 的 JSON。

**3. 误判阶梯级别的代价被量化了。** `cdn-standard` 上 `spoofed`（换个客户端库）就够，爬到 L5 多付 28 倍；`legacy-gov` 上 139 倍。

## 交叉点：什么时候值得逆向

`browser` 与 `signed` 都能拿下 `api-signed`，但成本结构相反：

| | 边际成本 | 一次性工时 | 谁的成本随规模摊薄 |
|---|---|---|---|
| `signed` | 近零 | 6h 逆向 | 工时 |
| `browser` | 高（真浏览器） | 1.5h 接线 | 工时（更少） |

采集量越大，两边的工时都摊薄，最后只剩边际成本在比——于是 `signed` 近零的边际必然反超。用 `--annual-records` 扫这个杠杆，交叉点清晰可见。而它落在哪，强烈依赖代理档位，因为 `browser` 的成本主要是**流量**（整页约 800 KB vs 精简 JSON 约 11 KB）：

| 代理档位 | 每 GB | 交叉点（年采集量） | 含义 |
|---|---|---|---|
| datacenter | $0.05 | **≈ 8.5 亿条** | 流量便宜，逆向很晚才回本 |
| residential | $4.00 | **≈ 1500 万条** | 流量贵，逆向早早回本 |

两个交叉点相差约 57 倍，恰好镜像代理价格比（80×）。**结论:逆向签名的价值不只取决于采集规模，还取决于你的代理有多贵——代理越贵，那 6 小时逆向越早回本。** 低于交叉点直接开浏览器，高于它花时间逆向。这把"要不要逆向"从经验判断变成了随规模与代理成本确定的量化决策。

复现（residential 档，跨过交叉点）：
```bash
botwall scan -p api-signed -a signed -a browser --proxy-tier residential --annual-records 10000000   # browser 赢
botwall scan -p api-signed -a signed -a browser --proxy-tier residential --annual-records 60000000   # signed 赢
```

## 当前结果的四条局限

这些数字**不能直接外推到真实站点**：

1. **`browser` 的整页流量已建模，但页面权重是可调的估计值。** 靶场落地页加载约 800 KB 确定性生成的资产（`app/assets.py`，用 `BW_PAGE_WEIGHT` 缩放），使 `browser` 相对 `signed` 的 ~48× 边际差如实显形。但真实站点从 0.5 MB 到 5 MB 不等，交叉点随之左右移动——上表的两个交叉点是本权重下的值，不是普适常数。此外 localhost 没有真实代理的延迟与失败率，这部分尚未建模。
2. **`tlsfront` 未实现**，L2 靠客户端自报 `X-BW-JA3`（`browser` 用 Playwright 的 extra headers 附上，与 HTTP 实现同一套开发模式替身）。真实的指纹伪装成本（换库）依然接近零，结论方向不变，绝对数字会变。
3. **`enveloped` / `traced` 的合成手段过得了靶场，过不了真实防御。** 真实运行时层会用更强的判据（WebGL 与设备类别的对照、轨迹与渲染帧率的相关性）识破合成，逼出真浏览器。所以它们测出的成本是**下界**。
4. **`dev_hours` 是申报值。** 逆向工时的估计天然不精确，结论应当对它做敏感性分析，而不是依赖单点值。上面的交叉点分析本身就是这种敏感性分析的一个例子。

5. **时间型防御对这套成本模型是隐形的。** 见下节。

## 一个关于本模型自身的发现：它看不见时间成本

靶场的 L5 加入几何任务（`gesture-guarded` profile）后，同一个 `browser` 攻击实现的实测对比：

| profile | 墙钟 | CPU | 模型算出的实测成本/万条 |
|---|---|---|---|
| `api-signed` | 2.81s | 0.523s | 0.01215 |
| `gesture-guarded` | 4.99s | 0.548s | 0.01217 |

**墙钟涨了 1.8 倍，模型算出的成本只变化 1.00 倍——等于完全没看见。**

原因在 `c_compute` 的定义：它按**攻击进程消耗的 CPU 时间**计价。而几何任务的成本是"必须真的等那几百毫秒"——等待不消耗 CPU，于是模型对它完全无感。

这不是测量误差，是模型的结构性盲区：**凡是把成本施加在时间而非算力上的防御（几何任务、强制延迟、异步挑战），这套按 CPU 计价的模型都会系统性低估其效力。**

而真实的云账单是按**实例小时**计费的——实例在等待时你照样付钱。所以正确的 `c_compute` 应该是：

```
c_compute = 墙钟秒数 / 并发数 × 实例单价
```

并发数是一个新参数：同一实例上跑 50 个并发采集任务时，等待的任务不独占实例，成本被摊薄；串行跑就不是。

**尚未修复**，因为它属于成本模型的扩展，而本项目当前的重心在靶场。这里如实记下来，连同上面那组实测数据——任何引用本模型结论的地方，都应当知道它对时间型防御是瞎的。

## 下一步

按对结果可信度的贡献排：

1. **让 `browser` 加载真实体积的页面资源**，或引入真实代理延迟与失败率。整页流量已建模（约 800 KB，可调），但页面权重仍是估计值、且未含代理延迟——这是当前交叉点数字的主要不确定来源。
2. **容器化 + cgroup 计量**。现在 CPU 用 `getrusage` 取（能透传捕获 chromium 这类孙进程的 CPU），够用但隔离不彻底。容器化后可顺带支持非 Python 的攻击实现。
3. **LLM 计量代理**。计量代理已能转发任意上游，加 token 记账即可接入 VLM 类攻击实现。
4. **`tlsfront`**，见根 README。
5. **`T_diag` 测量协议**。`--mode blind` 已能制造"无归因"环境，但"从失效到正确归因的工时"需要人参与，得设计一套可复现的实验流程。

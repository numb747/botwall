# Harness —— 成本核算与阶梯扫描

靶场是被测对象，harness 是量具。

```bash
costladder scan                             # 全 profile × 全攻击实现
costladder scan -p api-signed -a signed     # 指定组合
costladder scan --mode blind                # 测投毒与排障成本
costladder scan --proxy-tier residential    # 换代理档位重算
costladder attackers                        # 列出攻击实现及申报工时
costladder rates                            # 看当前价格表
```

---

## 计量是强制的

攻击实现拿到的 `CL_TARGET` 指向 harness 的计量反向代理，**不是靶场**。它不知道靶场的真实地址，因此无法绕过计量。

| 项 | 记账方式 | 攻击实现能否影响 |
|---|---|---|
| 请求数、字节数、状态码 | 计量代理 | 否 |
| 拦截原因码 | 计量代理解析 403 响应体 | 否 |
| CPU 时间 | `getrusage(RUSAGE_CHILDREN)` 前后差 | 否 |
| 记录真伪 | harness 调靶场的 `verify_record` | 否 |
| **逆向工时 `dev_hours`** | **manifest 申报** | **是** |

最后一行是唯一不可核实的量，所以它在输出里**永远与实测量分列**，只在 `total` 里合并。把二者悄悄加成一个数，读者就无法判断哪部分可信。

CPU 用 `RUSAGE_CHILDREN` 而不是墙钟：这个计数器只统计已回收的子进程，而靶场进程在整个测量期间一直活着不被回收，所以差值精确等于攻击进程的 CPU。墙钟里混着计量代理的转发开销，只作诊断量上报。

### 真值校验不能省

blind 模式下靶场返回 **HTTP 200 + 投毒数据**。只统计状态码会把投毒响应算成成功，从而高估通过率、低估重试放大系数 `R`、最终低估单位成本。harness 对每条记录调 `verify_record`，`R = 吐出条数 / 已验证为真的条数`。

## 攻击实现

它们之间**唯一的差别是 `headers()`**，也就是在成本阶梯上爬了几级。差异被压缩到一个方法上，测出来的成本差才只可能来自阶梯级别，不可能来自主循环写法的不同。

| | 级 | 多做了什么 | 申报工时 | 成本落在哪 |
|---|---|---|---|---|
| `naive` | L0 | 裸 GET | 0.1h | — |
| `spoofed` | L0 | 浏览器 UA + TLS 指纹 | 0.5h | 边际≈0 |
| `signed` | L1 | 复现 `derived` 档签名 | 6h | **一次性工时** |
| `enveloped` | L4 | 自洽环境快照 + `runtime` 档签名 | 10h | 一次性工时 |
| `browser` | L4 | 真浏览器跑站点自己的 `sign.js`，不逆向 | 1.5h | **持续边际** |
| `traced` | L5 | 合成类人轨迹 | 14h | 一次性工时 |

`browser` 是这里唯一走另一条经济路径的实现：它不逆向签名，让 Playwright 驱动一个真 Chromium 加载靶场页面、执行站点自己的 `signedFetch`。代价从"一次性逆向工时"换成了"每次采集都要跑一个浏览器"的持续边际成本——正是"能不能不用浏览器"这个论点的两端。它也是唯一真正付出浏览器 CPU 与整页流量的实现。

它过不了 `hardened` 的 paranoid WebGL 校验（headless 软件渲染是 SwiftShader），这个边界本身是一条结论：运行时层的严格档要逼出的正是**真实 GPU / 真实设备**，成本在那一步才真正跳到另一个量级。

### 一条靠测试强制的完整性约束

攻击实现**不许 import 靶场的 `app.signing`**。能 import 就等于抄答案，申报的工时和测出的成本全是假的。`test_attackers_do_not_import_range_internals` 用 AST 检查每个源文件（含公共骨架 `_base.py`），不靠自觉。

同样有测试禁止攻击实现内置任何指向外部主机的地址。

### 协议

```
输入   环境变量 CL_TARGET / CL_ITEMS_WANTED / CL_PAGE_SIZE
输出   stdout 逐行 JSONL，每行一条采到的记录
诊断   stderr（单独捕获，不参与计量）
退出   0 = 采够了，非 0 = 放弃
```

语言不限，进程边界就是接口边界。当前实现都是 Python，但换成 Go/Node 只要守住这个协议即可。

## 实测结果（v0.1）

`costladder scan -p cdn-standard -p api-signed -n 60`，价格表 v1，数据中心代理档。完整结果见 `results/v0.1-scan.json`。

```

naive        L0      0      ∞           ∞       0.02         ∞    ja3_absent
spoofed      L0     60   1.00×   1.50e-04       0.08      0.08    —
signed       L1     60   1.00×   1.60e-04       0.96      0.96    —

══ api-signed [diagnostic/gate] ══
```

实测列在重复运行之间会有几个百分点的波动，来自 CPU 计时噪声；这是量级结论，不是精确值。摊销列是确定性的（申报工时 × 价格表）。

### 三条读得出来的结论

**1. 纯 HTTP 方案的成本几乎全是一次性逆向工时，边际成本可以忽略。**

`signed` 的实测边际在 `1e-4` 量级，而它的摊销工时（在年采千万条下）是 `0.96`——差四个数量级。这正是成本模型里说 L1 特殊的原因：它付出的是一次性工时而非持续边际成本，所以**采集量越大越划算**。推论对防御方直接有用：针对这类对手，抬边际成本（加难度）几乎无效，抬一次性工时（加检查项数量和多样性）才有效。

**2. `browser` 的边际成本是 `signed` 的约 8 倍（数据中心档），却因为省掉逆向工时而在中等规模下总成本最低。** 这不是矛盾，是两条经济路径的分工——见下节的交叉点。

**3. 误判阶梯级别的代价被量化了。** `cdn-standard` 上 `spoofed`（换个客户端库）就够，爬到 L5 多付 28 倍；`legacy-gov` 上 139 倍。

## 交叉点：什么时候值得逆向

`browser` 与 `signed` 都能拿下 `api-signed`，但成本结构相反：

| | 边际成本 | 一次性工时 | 谁的成本随规模摊薄 |
|---|---|---|---|
| `signed` | 近零 | 6h 逆向 | 工时 |
| `browser` | 高（真浏览器） | 1.5h 接线 | 工时（更少） |

采集量越大，两边的工时都摊薄，最后只剩边际成本在比——于是 `signed` 近零的边际必然反超。用 `--annual-records` 扫这个杠杆（residential 代理档，让 `browser` 的整页流量成本显形）：

```
年采集量        signed 合计/万条    browser 合计/万条    最优
100,000              96.06               24.04         browser
10,000,000            0.97                0.27         browser
320,000,000           0.04                0.04         打平
500,000,000           0.03                0.03         signed
```

**交叉点在年采约 3.2 亿条**（本价格表下）。低于它，逆向不划算，直接开浏览器；高于它，那 6 小时逆向开始回本。这就是"要不要花时间逆向签名"这个真实决策的量化答案——它取决于采集规模，而不是取决于"能不能逆出来"。

复现：
```bash
costladder scan -p api-signed -a signed -a browser --proxy-tier residential --annual-records 320000000
```

（注意：localhost 靶场的页面很小、无真实代理延迟，所以 `browser` 的边际成本是**被低估**的，真实交叉点会更靠左。这条随下面的局限一起看。）

## 当前结果的四条局限

这些数字**不能直接外推到真实站点**：

1. **`browser` 的边际成本被低估。** 靶场页面只有几十 KB，真实站点动辄几 MB（JS/CSS/图片/字体），浏览器要全部加载；且 localhost 无真实代理延迟与失败率。所以阶梯上半段那 ~50× 的惩罚，这里只显出约 8×。真实差距更大，交叉点更靠左。
2. **`tlsfront` 未实现**，L2 靠客户端自报 `X-CL-JA3`（`browser` 用 Playwright 的 extra headers 附上，与 HTTP 实现同一套开发模式替身）。真实的指纹伪装成本（换库）依然接近零，结论方向不变，绝对数字会变。
3. **`enveloped` / `traced` 的合成手段过得了靶场，过不了真实防御。** 真实运行时层会用更强的判据（WebGL 与设备类别的对照、轨迹与渲染帧率的相关性）识破合成，逼出真浏览器。所以它们测出的成本是**下界**。
4. **`dev_hours` 是申报值。** 逆向工时的估计天然不精确，结论应当对它做敏感性分析，而不是依赖单点值。上面的交叉点分析本身就是这种敏感性分析的一个例子。

---

## 下一步

按对结果可信度的贡献排：

1. **让 `browser` 加载真实体积的页面资源**，或引入真实代理，让 ~50× 惩罚如实显形。这是当前交叉点数字唯一的大偏差来源。
2. **容器化 + cgroup 计量**。现在 CPU 用 `getrusage` 取（能透传捕获 chromium 这类孙进程的 CPU），够用但隔离不彻底。容器化后可顺带支持非 Python 的攻击实现。
3. **LLM 计量代理**。计量代理已能转发任意上游，加 token 记账即可接入 VLM 类攻击实现。
4. **`tlsfront`**，见根 README。
5. **`T_diag` 测量协议**。`--mode blind` 已能制造"无归因"环境，但"从失效到正确归因的工时"需要人参与，得设计一套可复现的实验流程。

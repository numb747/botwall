# Harness —— 成本核算与阶梯扫描

靶场是被测对象，harness 是量具。

```bash
costladder scan                             # 全 profile × 全攻击实现
costladder scan -p api-signed -a signed     # 指定组合
costladder scan --mode blind                # 测投毒与排障成本
costladder scan --proxy-tier residential    # 换代理档位重算
costladder attackers                        # 列出攻击实现及申报工时
costladder rates                            # 看当前价格表
```

---

## 计量是强制的

攻击实现拿到的 `CL_TARGET` 指向 harness 的计量反向代理，**不是靶场**。它不知道靶场的真实地址，因此无法绕过计量。

| 项 | 记账方式 | 攻击实现能否影响 |
|---|---|---|
| 请求数、字节数、状态码 | 计量代理 | 否 |
| 拦截原因码 | 计量代理解析 403 响应体 | 否 |
| CPU 时间 | `getrusage(RUSAGE_CHILDREN)` 前后差 | 否 |
| 记录真伪 | harness 调靶场的 `verify_record` | 否 |
| **逆向工时 `dev_hours`** | **manifest 申报** | **是** |

最后一行是唯一不可核实的量，所以它在输出里**永远与实测量分列**，只在 `total` 里合并。把二者悄悄加成一个数，读者就无法判断哪部分可信。

CPU 用 `RUSAGE_CHILDREN` 而不是墙钟：这个计数器只统计已回收的子进程，而靶场进程在整个测量期间一直活着不被回收，所以差值精确等于攻击进程的 CPU。墙钟里混着计量代理的转发开销，只作诊断量上报。

### 真值校验不能省

blind 模式下靶场返回 **HTTP 200 + 投毒数据**。只统计状态码会把投毒响应算成成功，从而高估通过率、低估重试放大系数 `R`、最终低估单位成本。harness 对每条记录调 `verify_record`，`R = 吐出条数 / 已验证为真的条数`。

## 攻击实现

它们之间**唯一的差别是 `headers()`**，也就是在成本阶梯上爬了几级。差异被压缩到一个方法上，测出来的成本差才只可能来自阶梯级别，不可能来自主循环写法的不同。

| | 级 | 多做了什么 | 申报工时 |
|---|---|---|---|
| `naive` | L0 | 裸 GET | 0.1h |
| `spoofed` | L0 | 浏览器 UA + TLS 指纹 | 0.5h |
| `signed` | L1 | 复现 `derived` 档签名 | 6h |
| `enveloped` | L4 | 自洽环境快照 + `runtime` 档签名 | 10h |
| `traced` | L5 | 合成类人轨迹 | 14h |

### 一条靠测试强制的完整性约束

攻击实现**不许 import 靶场的 `app.signing`**。能 import 就等于抄答案，申报的工时和测出的成本全是假的。`test_attackers_do_not_import_range_internals` 用 AST 检查每个源文件（含公共骨架 `_base.py`），不靠自觉。

同样有测试禁止攻击实现内置任何指向外部主机的地址。

### 协议

```
输入   环境变量 CL_TARGET / CL_ITEMS_WANTED / CL_PAGE_SIZE
输出   stdout 逐行 JSONL，每行一条采到的记录
诊断   stderr（单独捕获，不参与计量）
退出   0 = 采够了，非 0 = 放弃
```

语言不限，进程边界就是接口边界。当前实现都是 Python，但换成 Go/Node 只要守住这个协议即可。

## 实测结果（v0.1）

`costladder scan -p cdn-standard -p api-signed -n 100`，价格表 v1，数据中心代理档。完整结果见 `results/v0.1-scan.json`。

实测列在重复运行之间会有几个百分点的波动，来自 CPU 计时噪声；这是量级结论，不是精确值。
摊销列是确定性的（申报工时 × 价格表）。

### 三条读得出来的结论

**1. 纯 HTTP 方案的成本几乎全是一次性逆向工时，边际成本可以忽略。**

实测边际成本在 `1e-4` 量级，摊销工时在 `0.08–2.24` 量级——差了四个数量级。这正是成本模型里说 L1 特殊的原因：它付出的是一次性工时而非持续边际成本，所以**采集量越大越划算**。

推论对防御方也成立：针对这类对手，抬边际成本（加难度）几乎没用，抬一次性工时（加检查项的数量和多样性）才有用。而后者对大规模采集方的效果同样会被摊薄——这是个结构性的不利局面。

**2. 误判阶梯级别的代价是量化的。** `cdn-standard` 上 `spoofed`（换个客户端库）就够，爬到 L5 要多付 28 倍。`legacy-gov` 上这个倍数是 139。

**3. 五个 profile 里有四个的最优解都低于人工打码地板线（$15/万条）几个数量级。** 唯一的例外是根本采不到数据的组合（∞）。这说明在当前这套防御强度下，自动化相对人工有压倒性的经济优势——但见下面第 1 条局限，这个结论目前是被高估的。

## 当前结果的四条局限

这些数字**不能直接外推到真实站点**：

1. **没有真实浏览器攻击实现。** 阶梯 L4/L5 的 ~50× 边际成本惩罚（浏览器要拉 JS/CSS/图片，代理流量差两个数量级）在当前结果里完全没有体现——现有实现全是纯 HTTP，只是多发几个头。所以 `traced` 的成本是**下界**，不是真实成本。
2. **靶场跑在 localhost，没有真实代理开销。** `--proxy-tier residential` 只是按字节数重算，反映不了住宅代理的延迟和失败率。
3. **`tlsfront` 未实现**，L2 靠客户端自报 `X-CL-JA3`。真实的指纹伪装成本（换库）依然接近零，所以结论方向不变，但绝对数字会变。
4. **`dev_hours` 是申报值。** 逆向工时的估计天然不精确，结论应当对它做敏感性分析，而不是依赖单点值。

## 下一步

按对结果可信度的贡献排：

1. **真实浏览器攻击实现**（Playwright）。当前最大的缺口——没有它，阶梯上半段的成本差就是假的。
2. **容器化 + cgroup 计量**。现在 CPU 用 `getrusage` 取，够用但隔离不彻底。容器化后可以顺带支持非 Python 的攻击实现。
3. **LLM 计量代理**。计量代理已经能转发任意上游，加 token 记账即可接入 VLM 类攻击实现。
4. **`tlsfront`**，见根 README。
5. **`T_diag` 测量协议**。`--mode blind` 已经能制造"无归因"的环境，但"从失效到正确归因的工时"需要人参与，得设计一套可复现的实验流程。

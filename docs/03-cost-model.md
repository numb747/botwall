# 成本模型

## 单位：每万条成功数据的全成本

记 `C₁₀ₖ` 为采到一万条**有效**数据的总成本（美元）。所有比较都以此为单位，因为它是唯一能直接对接业务毛利的口径。

```
C₁₀ₖ = 10000 × R × (c_proxy + c_compute + c_solve + c_account) + A_dev
```

| 符号 | 含义 |
|---|---|
| `R` | **重试放大系数** = 1 / 成功率 |
| `c_proxy` | 单次请求的代理成本 |
| `c_compute` | 单次请求的算力成本 |
| `c_solve` | 单次请求摊到的求解成本（打码、模型调用） |
| `c_account` | 单次请求摊到的账号成本 |
| `A_dev` | 一次性开发与维护成本的摊销 |

### 重试放大系数 `R` 是最容易被漏掉的一项

通过率 70% 意味着所有边际成本乘 1.43，通过率 40% 意味着乘 2.5。讨论方案时只报"能不能过"而不报通过率，成本结论就是错的。

`R` 还必须区分**失败类型**，因为它们的成本不同：
- 软失败（限流、需重试）：只损失一次请求的成本
- 硬失败（IP 被封、账号被封）：损失该 IP/账号的剩余价值，成本高得多

### 各项的测量方式

**`c_proxy`** — 代理按流量计费，所以它由**每请求字节数**决定，而不是请求数：
```
c_proxy = 每请求字节数(含响应) × 代理单价($/GB)
```
这带来一个常被忽略的推论：**浏览器方案的代理成本远高于 HTTP 方案**，因为浏览器会加载 JS、CSS、图片、字体等一整套资源。同一个页面，纯 HTTP 取 30 KB，浏览器可能取 3 MB——代理账单差 100 倍。这项和算力成本是叠加的，不是二选一。

**`c_compute`** — 由并发密度决定：
```
c_compute = 实例单价($/小时) / (单实例并发数 × 3600 / 单请求耗时秒)
```
靶场用 cgroup 记账，不接受自报数字。

**`c_solve`** — 分三种攻击者档位，各自的计价方式不同：
| 档位 | 计价 |
|---|---|
| 自训模型 | 一次性训练成本摊销 + 近零边际推理成本 |
| 开源权重 VLM 自托管 | 折算为 `c_compute` |
| 前沿 VLM API | 按 token 计价，**由 harness 的计量代理记账** |
| 人工打码平台 | 按次计价，约 $0.5–3 / 千次，即 **$0.0005–0.003 / 次** |

最后一行是整个模型里的**价格地板**。任何自动化方案，如果单次成本高于人工打码，它在经济上就没有存在理由——攻击者会直接买人工。这条线把"这个方案值不值得做"变成一个可计算、可反驳的判断，而不是观点。

**`A_dev`** — 摊销期由**目标站的改版频率**决定，不是由项目周期决定。一个每季度改版的站，签名逆向的工时要按三个月摊销。这项在阶梯的 L1 级权重极高（见下）。

## 成本阶梯

阶梯的级号与靶场的层号对应：**被第 N 层拦住，你至少要爬到第 N 级**。

| 级别 | 方案 | 相对成本量级 | 被迫停在这里的原因 |
|---|---|---|---|
| **L0** | 纯 HTTP + 数据中心 IP | 1× | — |
| **L1** | HTTP + 复现签名 | ~1× 边际，但有一次性逆向工时 | L3 协议层 |
| **L2** | HTTP + 住宅/移动 IP | ~10× | L1 网络层 |
| **L3** | 轻量 JS 引擎（执行 JS，不渲染） | ~15× | L3 协议层的 `runtime` 档 |
| **L4** | 完整无头浏览器 + 指纹伪装 | ~50× | L4 运行时层 |
| **L5** | 真浏览器 + 可信交互 / 人工介入 | ~200× | L5 行为层 |

**"相对成本量级"是待测量的对象，不是预设结论。** 上表的数字是立项时的先验估计，靶场存在的意义就是把它们替换成实测值。任何引用这些数字的地方都必须标注是先验还是实测。

### L1 在模型里是特殊的

其他所有级别付出的是**持续的边际成本**——每多采一条数据，就多花一次代理费和算力费。

而 L1 付出的是**一次性的逆向工时**：签名逆出来之后，单次请求的边际成本和 L0 几乎相同。

这意味着 L1 的经济学完全不同：

```
L1 是否划算 = (被顶到 L3/L4 的边际成本增量 × 预期总采集量) > 逆向工时成本
```

采集量越大、摊销期越长，逆向就越划算。所以**签名逆向是唯一一项"规模越大回报越高"的能力**，也是为什么它是这门手艺里最值钱的部分。

同时它也是风险最高的一项：目标站改版会让 `A_dev` 重新计一次。所以完整的判断还要带上改版频率：

```
年化 A_dev = 单次逆向工时成本 × 年改版次数
```

### 阶梯不是单调的

一个常见且昂贵的误判：在 L2 传输层被拦，误以为"要上浏览器"，直接跳到 L4。

而 L2 的正确应对是换一个具备 TLS 指纹伪装能力的 HTTP 客户端——**成本增量几乎为零**。跳到 L4 意味着白白付出约 50 倍成本。

这正是靶场归因能力的直接价值：`diagnostic` 模式会告诉你被 L2 拦了、原因是 `ja3_known_script_client`，于是你知道该换库而不是换架构。

## 排障工时：`blind` 模式下的第三项成本

真实站点不会告诉你哪一层拦了你。管线昨天好好的今天全挂，定位原因的工时是真实成本，而且它在所有现有评测里都不被计入。

靶场的 `blind` 模式（被拦时返回结构合法但内容虚假的数据，不给任何失败信号）专门测量这一项：

```
T_diag = 从管线失效到正确归因的工时
```

同一个 profile 分别在 `diagnostic` 和 `blind` 模式下跑，`T_diag` 的差值就是"归因能力"的货币化价值。这项数据目前不存在于任何公开研究中。

## 输出形态

**不是 leaderboard，是决策表。** 每一行回答一个工程问题：

| Profile | 最优级别 | `C₁₀ₖ` | `R` | 关键约束 |
|---|---|---|---|---|
| `cdn-standard` | L0 + 指纹伪装客户端 | 待测 | 待测 | L2 `ja3_ua_mismatch` |
| `api-signed` | L1 | 待测 | 待测 | 签名 `derived` 档，`A_dev` 主导 |
| `hardened` | 待测 | 待测 | 待测 | `score` 形态，单层失败可补偿 |

配一张**成本–通过率的帕累托前沿图**：横轴 `C₁₀ₖ`，纵轴成功率，每个点是一个（级别 × profile）组合，并标出 $0.0005/次 的人工打码地板线。

这张图是整个项目的结论。

## 记账诚信

所有成本必须由 harness 记账，不接受实现方自报：

- **token 消耗**：攻击实现跑在容器内，LLM 调用强制走计量代理，token 数由代理记录
- **CPU / 内存**：cgroup 记账
- **网络字节数**：容器网络命名空间记账
- **墙钟**：runner 记录

现有工作普遍是"作者在论文里写我们花了 $X"——不可复现，不可比较。计量在 harness 层强制执行，是本项目的实质技术贡献之一。

# 项目边界

## 一句话

**本项目只在自己的靶场上测量成本，不针对任何第三方线上服务。**

## 具体的做与不做

### 做

- 复现各层防御的**最小实现**，做成可独立开关的本地靶场
- 在靶场上测量不同技术路径的单位成本
- 讨论防御手段的**原理**、信号来源、以及它们在成本上的含义
- 讨论采集工程的方法论：入口选择、归因、降级、可观测性

### 不做

- **不复现任何具体商业站点的签名算法或防御实现。** 靶场里的签名方案是自造的，只在结构上与真实方案同构（时效 + 随机数 + 盐 + 排序参数序列化），不含任何厂商的实际逻辑。文档中提及真实厂商的方案名称时，仅作为"这类防御真实存在于生产环境"的说明，不提供其实现细节。
- **不把第三方线上站点作为测量目标。** 三条独立理由，任何一条都足以否决：不可复现（目标改版后数据即失效）、不可归因（真实站点多层叠加，测不出单层贡献）、无授权。
- **不提供针对线上服务的求解器、绕过脚本或自动化工具。** 仓库内的攻击侧实现只面向本地靶场，不携带任何指向外部主机的目标配置。
- **不收集、不分发任何真实个人数据。** 靶场提供的"被采集数据"全部为程序生成的合成数据。

## 为什么这条线值得认真画

不是出于保守。三个实际理由：

**可复现性。** 以线上站点为目标的测量结果，寿命取决于对方的发版节奏。一份两周就过期的成本数据没有引用价值，也没有工程价值。靶场的 profile 是版本钉死的，同一个 profile 在任何机器上跑出的结果必须一致。

**可归因性。** 真实站点把六层防御叠在一起且不告诉你哪层生效，因此无法测量单层的成本贡献。而单层贡献恰恰是本项目要产出的核心数据——"该换库还是该换架构"这个判断完全依赖于它。

**可用性。** 一个携带线上绕过能力的仓库，无法被企业内部使用、无法被引用、也无法放到台面上讨论。而一个纯本地的靶场加成本模型，任何团队都能直接拿去做技术选型和回归测试。

这不是在能力和合规之间做取舍。**靶场化同时提高了技术价值和可用性**——它是更好的工程方案，合规只是附带结果。

## 合规提醒（面向使用者）

本项目的方法论可以应用于真实采集工作。在那之前，采集方自己需要确认的事项至少包括：目标站点的 `robots.txt` 与服务条款、数据是否包含个人信息、是否涉及著作权客体、是否需要登录（登录后数据与公开数据的法律性质不同）、以及请求频率是否对目标构成实际负担。

这些判断因司法辖区、数据类型和使用目的而异，本项目不提供法律建议，也不对使用者的行为负责。

## 先行工作

本项目与以下工作在问题意识上互补，而非竞争——它们测量模型能力，本项目测量采集成本：

- [Open CaptchaWorld](https://github.com/MetaAgentX/OpenCaptchaWorld) (NeurIPS 2025)
- [Halligan](https://www.usenix.org/conference/usenixsecurity25/presentation/teoh) (USENIX Security '25)
- MCA-Bench (AAAI)、CAPTCHA-X、CAPTURE、COGNITION

其中 COGNITION 的发布策略（artifact 只含评测组件，明确排除线上自动化与生产级绕过设施）与本项目的边界一致，可作为先例参照。

# 靶场分层设计规格

靶场是一个**可逐层开关的反自动化防御复现实现**。它不模仿任何具体站点，而是把真实站点上叠加在一起的防御手段拆成六个互相独立的层，每层可以单独启用、单独调强度。

拆开的目的只有一个：**让"我被拦了"变成"我被第 N 层拦了，因为 X"**。真实站点不会告诉你这个，所以你没法归因；归因不了，就没法判断该停在成本阶梯的哪一级。

---

## 设计原则

**1. 每层只检验一个维度，且维度之间不重叠。**
L2 只看 TLS 指纹，绝不顺带看 UA；L4 只看 JS 运行时环境，绝不顺带看行为轨迹。有重叠就归因不了。

**2. 每层独立开关 + 独立强度档。**
一个层至少有 `off / lenient / strict` 三档。强度是连续旋钮，不是布尔——真实世界的风控阈值就是这么调的，成本曲线也只有在旋钮上扫描才画得出来。

**3. 判定结果必须携带归因信息，但归因是否可见由模式决定。**
见下方「两种响应模式」。

**4. 层与层之间不共享状态，除了一个显式的 `RangeState`。**
频率计数、nonce 重放表、会话记录集中放在 `RangeState` 里，层只读写自己那部分。这样任何一层都能被单独拔掉而不破坏其他层。

**5. 靶场自身不产生随机密钥。**
所有 salt、密钥、JA3 白名单都写在 profile 里，版本钉死。同一个 profile 在任何机器上跑出的结果必须一致，否则成本数据不可比。

---

## 两种响应模式

这是靶场最重要的一个设计，直接来自真实世界的一条观察：**成熟的防御方不会告诉你哪里失败了。** DataDome 对不信任的客户端直接返回空页或假数据，而不是弹验证码——不告诉攻击者失败原因，是最有效的反制之一。

| 模式 | 被拦时的行为 | 用途 |
|---|---|---|
| `diagnostic` | 返回 `403` + JSON，明确写出被哪一层拦、原因码、诊断细节 | 开发、教学、回归测试 |
| `blind` | 返回 `200` + **结构合法但内容虚假的数据**，不给任何失败信号 | 测量"没有归因帮助时，定位一次失败要花多久" |

`blind` 模式不是装饰。它测量的是采集工程里最贵、也最少被量化的一项成本：**排障工时**。管线昨天好好的今天全挂了，你花两小时定位出是 TLS 指纹变了，这两小时是真实成本，而且它在所有现有的评测里都不被计入。

## 六层规格

层号即成本阶梯的台阶号：**被第 N 层拦住，意味着你至少要爬到阶梯的第 N 级**。

### L1 — 网络层 `l1_network`

**检验对象**：来源 IP 本身，以及该 IP 的请求节奏。

**信号**
- IP 所属段类型：数据中心 / 住宅 / 移动（靶场用一份内置的 ASN 分类表判定，可替换）
- 滑动窗口内的请求频率
- 单 IP 的会话并发数

**强度档**
| 档 | 行为 |
|---|---|
| `lenient` | 仅频率限制，窗口宽松（如 60 req/min） |
| `strict` | 频率收紧 + 拒绝数据中心 IP 段 |
| `paranoid` | 上述之外，要求单 IP 会话并发 ≤ 2 |

**被它拦住意味着**：你的代理档位不够。对应阶梯上从数据中心 IP 升级到住宅/移动 IP，这是成本倍数最直观的一跳（住宅代理按流量计费，通常比数据中心贵一到两个数量级）。

**原因码**：`rate_exceeded` / `datacenter_asn` / `session_concurrency`

---

### L2 — 传输层 `l2_transport`

**检验对象**：TLS 与 HTTP/2 的握手指纹。与应用层完全无关。

**信号**
- JA3 / JA4 指纹（来自 ClientHello 的密码套件、扩展、椭圆曲线的有序组合）
- HTTP/2 SETTINGS 帧的参数顺序与取值（即 Akamai 指纹）
- 指纹与 `User-Agent` 声明的浏览器是否**一致**

最后一条是关键。单看 JA3 只能判断"这不是浏览器"；而 JA3 与 UA 的**交叉矛盾**（声称自己是 Chrome，握手却是 Python `requests` 的形状）是强度高得多的信号，因为它无法通过换一个 UA 绕过。

**强度档**
| 档 | 行为 |
|---|---|
| `lenient` | 仅拒绝已知的脚本库指纹（requests / urllib / Go 默认客户端） |
| `strict` | 要求 JA3 命中真实浏览器白名单 |
| `paranoid` | 上述之外，要求 JA3 与 UA 声明的浏览器版本族匹配 |

**被它拦住意味着**：你的 HTTP 客户端选型不对。对应阶梯上从 `requests` 换到具备指纹伪装能力的客户端（`curl_cffi` 一类）。这一跳的**成本增量几乎为零**——换个库而已——所以它是整条阶梯上性价比最高的一级，但也是最容易被忽略的一级。很多人在这里被拦，却误判成"要上浏览器"，直接从 L2 跳到 L5，白白付出 50 倍成本。

**实现说明**：TLS 指纹无法在应用层中间件里拿到，需要一个前置的 TLS 嗅探代理解析 ClientHello 原始字节、计算 JA3，再以 `X-BW-JA3` 头转发给应用。该组件是 `range/tlsfront`。在纯 HTTP 的本地开发模式下该头可被客户端伪造——这是**有意为之**，便于单测；启用 `tlsfront` 后代理会强制覆盖该头。

**原因码**：`ja3_known_script_client` / `ja3_not_in_allowlist` / `ja3_ua_mismatch` / `h2_fingerprint_mismatch`

---

### L3 — 协议层 `l3_protocol` ★

**检验对象**：请求本身携带的签名。**这是整条阶梯上成本差最大的一道分水岭。**

国内主流站点的真实门槛几乎都在这一层，而不在验证码：抖音的 `a_bogus` / `msToken`、小红书的 `X-s` / `X-t`、B 站的 `wbi` 签名、知乎的 `x-zse-96`、淘宝 mtop 的 `sign`。签名能不能脱离浏览器静态复现，直接决定你停在阶梯的 L1 还是被顶到 L4。

**签名方案**（靶场内置，分三档难度，均可独立逆向）

请求必须携带三个头：

```
X-BW-Ts:    毫秒时间戳
X-BW-Nonce: 客户端生成的随机串
X-BW-Sign:  签名值
```

签名计算：

```
payload = method + "\n" + path + "\n" + canonical_query + "\n" + ts + "\n" + nonce
sign    = hex(sha256(salt + payload))[:32]
```

`canonical_query` 为查询参数按 key 字典序排序后以 `&` 连接。三档难度的区别**只在 `salt` 从哪来**：

| 档 | salt 来源 | 可静态逆向？ | 把你顶到 |
|---|---|---|---|
| `static` | 明文写在 `/static/sign.js` 里 | 是，读一遍 JS 即可 | **L1**（纯 HTTP + 复现签名） |
| `derived` | 由页面下发的种子经一段混淆 JS 变换得到，变换过程含字符串拼接与位运算 | 是，但要读懂混淆代码 | **L1**（代价是逆向工时） |
| `runtime` | salt 的一部分取自浏览器运行时（如 `navigator` 若干属性的哈希），JS 里拿不到完整值 | 否 | **L3+**（被迫跑 JS 引擎） |
| `vm` | salt 绑定 L4 的 VM 执行结果 | 否 | **L3+**，且**纯靠构造 JSON 绝对过不去** |

`vm` 档与 `runtime` 档的区别是关键：`runtime` 绑的是**环境快照**，手写一份自洽 JSON 就能过；`vm` 绑的是**执行结果**，只能真的跑出来。这是 L3 与 L4 之间最强的耦合点——不跑完 VM 就签不出名。

服务端同时校验：
- **时效**：`ts` 与服务器时间偏差超过窗口（默认 60s）即拒
- **重放**：`nonce` 在 `RangeState` 的重放表里出现过即拒

这两条是刻意加的。它们让"抓一个包反复重放"这条最廉价的路径失效，逼迫实现方真正复现签名算法——而这正是签名逆向这门手艺的实际要求。

**被它拦住意味着**：你还没复现签名。这是唯一一层"付出的是**一次性逆向工时**而非**持续边际成本**"的防御——逆出来之后单次请求成本几乎不变，逆不出来就只能整条管线升级到浏览器方案。所以它在成本模型里的处理方式与其他层不同，见 `03-cost-model.md`。

**原因码**：`sign_missing` / `sign_mismatch` / `ts_expired` / `nonce_replayed`

---

### L4 — 运行时层 `l4_runtime`

**检验对象**：客户端有没有真实的 JS 运行时。两种机制，用 `options.mechanism` 选：`env` / `vm` / `both`。

#### 机制一：`env` —— 检验环境快照的自洽性

不问"你是不是浏览器"（没法问），而是问"你**声称**的这套环境属性之间有没有互相矛盾"。伪造单个属性很容易，让几十个属性互相自洽很难。

**但这终究是"校验声明"，不是"要求证明"。** 手写一份互不矛盾的 JSON 就能过——harness 里的 `enveloped.py` 正是这么干的。保留它有教学价值，也如实反映了相当多生产环境的真实强度。

**信号**（客户端需上报 `X-BW-Env`，内容为一段 JS 采集后编码的环境快照）
- `navigator` 属性组间的一致性：`userAgent` / `platform` / `oscpu` / `hardwareConcurrency` / `languages`
- WebGL `vendor` + `renderer` 与声称的 OS/浏览器是否匹配
- Canvas 指纹的稳定性与合理性（全零、常见 headless 已知值、跨请求跳变均可疑）
- 自动化痕迹：`navigator.webdriver`、CDP 注入残留、异常的 `window` 属性
- 环境快照的**生成耗时**是否在人类设备的合理区间

**强度档**
| 档 | 行为 |
|---|---|
| `lenient` | 仅检查显式自动化标志（`webdriver` 等） |
| `strict` | 加上 navigator 属性组交叉一致性 |
| `paranoid` | 加上 WebGL / Canvas 与声明平台的匹配 |

**原因码**：`webdriver_flag` / `navigator_inconsistent` / `webgl_mismatch` / `canvas_suspicious` / `env_timing_implausible`

#### 机制二：`vm` —— 随机化虚拟机挑战 ★

服务端按会话确定性地生成一段**栈式虚拟机字节码**，连同一个解释它的 JS 一起下发；客户端必须真的执行，才能算出 token。

真正的门槛不是混淆，而是**程序本身每会话都不同**——预先逆向无效。这是瑞数五代、`acw_sc__v2`、`a_bogus` 那一类防御的核心原理。实现见 `range/app/vm.py`。

**指令集**：16 个操作码的栈机，32 位无符号运算。`PUSH` / `LOAD` / `DUP` / `SWAP` / `DROP` / `ADD` / `SUB` / `MUL` / `XOR` / `AND` / `OR` / `SHL` / `SHR` / `ROTL` / `NOT` / `MIX`（murmur3 finalizer）。

**强度档**
| 档 | 行为 | 对应的攻防状态 |
|---|---|---|
| `lenient` | 操作码编号固定，程序 64 条 | 攻击方写一次 VM 模拟器就能一劳永逸（现实中被攻破的状态） |
| `strict` | **操作码编号逐会话打乱**，程序 160 条 | 写死的模拟器每次失效，必须动态提取操作码表，或干脆跑 JS 引擎 |
| `paranoid` | 打乱 + 程序 400 条 | 同上，执行成本更高 |

**两条关键设计**

*无状态可复现。* 程序完全由 `session` 派生，服务端不存任何东西就能在校验时复算出同一段字节码；同一个 session 在任何机器上拿到同一段程序。

*每个请求都要跑一次。* VM 的输入含 `ts` 与 `nonce`，所以 token 不是每会话一个常量，跑一次不能跨请求重放。这也让防御对攻击方产生**可度量的 CPU 成本**。

为此，程序的收尾段把每个输入各经一个 32 位双射（乘奇数 + 循环移位）折进累加器。这不是锦上添花：纯自由随机的主体有 **80% 以上**的概率把某个输入的影响彻底抹掉（`AND`/`OR`/`SHR`/乘偶数都销毁信息位），那样 token 就退化成每会话一个常量，"每个请求都要执行"这个性质直接失效。这个数字是实测的，不是估计。

**跨语言一致性**：服务端用 Python 算期望值、客户端用 JS 算实际值，两端的 32 位语义必须逐位一致——差一位就变成随机拒绝合法客户端。测试套件真的起一个 Node 进程去执行发出的 JS 并比对（`test_python_and_node_agree`）。最容易出问题的是乘法：JS 必须用 `Math.imul`，普通 `*` 超过 2^53 就丢精度。

**原因码**：`vm_session_missing` / `vm_token_missing` / `vm_input_malformed` / `vm_token_mismatch`

---

**`env` 可以纯靠构造 JSON 骗过，`vm` 不行。** 这个区别是本层强弱的分水岭，也是真实防御与朴素指纹校验的分水岭。

**被本层拦住意味着**：你需要一个真实的 JS 运行时。`env` 机制下对应"轻量 JS 引擎"，`vm` 机制下则必须真的执行服务端下发的代码。

### L5 — 行为层 `l5_behavior`

**检验对象**：交互事件序列的统计特征。

**信号**（客户端需上报事件轨迹）
- 事件间隔的**方差与分布形状**——人类的间隔是长尾的，脚本的往往接近常数或均匀分布
- 指针路径的曲率与加速度连续性——直线匀速位移是最强的机器信号
- 事件序列的完整性——真实点击前必有 `mousemove`、`mousedown`，缺项即可疑
- 页面停留时长与内容量的比例关系

**强度档**
| 档 | 行为 |
|---|---|
| `lenient` | 仅要求轨迹存在且事件序列完整 |
| `strict` | 加上间隔分布的方差下限 |
| `paranoid` | 加上路径曲率与加速度连续性 |

**被它拦住意味着**：你需要驱动一个真实浏览器并产生可信的交互。这是阶梯上最贵的一级。

**原因码**：`trace_missing` / `event_sequence_incomplete` / `interval_variance_low` / `path_unnatural`

### L6 — 验证码层 `l6_captcha`

**检验对象**：一道显式的题目。

**这一层在默认 profile 里是关闭的，而且它的位置在最后——这是刻意的设计表达。**

在现代站点上，验证码不是常规关卡，而是**失败模式**：L1–L5 中某一层已经对你产生了怀疑，系统才用一道题来惩罚你。你看到验证码，说明你在前面某层已经露馅了。因此靶场里 L6 的触发条件不是"每次请求都出题"，而是：

```
前五层累计风险分 ≥ 阈值 → 触发 L6
```

这个结构让"不触发挑战"成为一个可测量的目标，而不是一句口号。它也解释了为什么"研究验证码强度"是在研究症状：真正决定成本的是你在 L1–L5 上的保真度。

**提供的题型**（仅为让阶梯末端有一个具体落点，不是本项目的研究重点）
- `static_image`：服务端生成的扭曲字符图。**保留它只是为了如实反映一个事实**——这种验证码在面向消费者的大流量站点已基本绝迹，但在政企与传统行业后台（招投标、司法文书、工商、教务、银行后台）仍大量存在，而那正是相当一部分采集业务的实际目标。
- `slider`：滑块，判定同时依赖缺口位置与轨迹质量（轨迹部分复用 L5 的判据）。
- `pow`：工作量证明，不问你是不是人，只让每次请求付出可度量的 CPU 成本。

**原因码**：`captcha_required` / `captcha_failed`

## 风险分与层间协作

每层返回的不是布尔值，而是一个带分值的判定：

```python
Verdict(layer="L2", passed=False, score=0.8, reason="ja3_ua_mismatch", detail={...})
```

`RangeState` 累加各层分值。这允许两种 profile 形态：

- **硬闸门式**（`gate`）：任一层 `passed=False` 立即拒绝。归因清晰，适合逐层测量单层成本。
- **评分式**（`score`）：累计分超阈值才拒绝，单层失败可被其他层的高保真度补偿。更接近真实商业风控，也更难归因——这正是要测的东西。

两种形态下同一套攻击实现的成本差，本身就是一个值得发表的结果。

## Profile：把六层组合成站点画像

Profile 是一份钉死的 YAML，描述某一类站点的防御组合。内置四份：

| Profile | 组合 | 对应现实 |
|---|---|---|
| `open` | 全关 | 基线，用于测量纯采集成本本身 |
| `legacy-gov` | L1 `lenient` + L6 `static_image` | 政企/传统行业后台 |
| `cdn-standard` | L1 `strict` + L2 `strict` | 挂了标准 CDN 防护的普通站点 |
| `api-signed` | L1 `strict` + L2 `strict` + L3 `derived` | 国内主流内容平台的 Web 端 |
| `hardened` | 六层全开，`score` 形态 | 高价值目标 |
| `vm-guarded` | L1+L2 `strict` + L3 `salt_mode: vm` + L4 `mechanism: vm` | 瑞数 / acw_sc__v2 / a_bogus 那一类 |

`vm-guarded` 是唯一一个**纯靠构造 JSON 绝对过不去**的 profile：不跑完服务端现场下发的随机字节码就签不出名。harness 里的五个纯 HTTP 攻击实现在它上面全部为 ∞，只有真浏览器过得去。

**Profile 是实验的自变量，成本是因变量。** 所有结果都必须标注 profile 版本号，否则不可比。

## 明确不做的事

- **不复现任何具体商业站点的签名算法或防御实现。** 靶场里的签名方案是自造的，只在结构上与真实方案同构（时效 + 随机数 + 盐 + 排序参数），不含任何厂商的实际逻辑。
- **不把真实商业站点作为测量目标。** 真站会改版（数据一周就过期）、多层叠加无法单层归因、且无授权。这三条里任何一条都足以否决，合起来没有讨论余地。
- **不提供针对线上服务的求解器。** 见 `04-scope.md`。

靶场的价值在于它是**可复现、可归因、可授权**的。这三点真实站点一个都不具备。
